# Code review after the restructure (2026-11-13)

Step 4 of the session-cost restructure. **Nothing here is fixed; the owner picks.** Most severe first.

**How it was done.** Scripts and measurements, then reading the code each one pointed at; not a line-by-line read of every file.
- Static scans of `src/` for unused imports, dead functions and exports, unused CSS classes, hover rules, `title` hints, DOM or clock use in the core, newer JavaScript and CSS features.
- A real browser (Chromium, 360 px wide, touch, CPU slowed 4x to stand in for a phone): 900 seeded taps on a new game and 900 on a save after 52 simulated weeks, measuring every control's size, sideways overflow, and the time each tap took to redraw.
- Save size and draw cost in Node on the same 52-week save.
- Not covered: Safari itself (Chromium was used), a real device, VoiceOver, and the 27 tap actions the step 3 comparison never reached (hall building, buying a hall, the buzz, a critical, heists, raid answers, the new-fight controls).

Severity: **High** = will break or lose something in a phone WebView. **Medium** = breaks a CLAUDE.md rule or will be felt in play. **Low** = tidy-up.

## High

### 1. A failed save is silent, and three full slots can pass the storage limit
- `save.js saveGame` returns whether the write worked. All five callers ignore it (`app.js:58` in `setState`, `actions.js:105`, `116`, `286`, `405`). `storageSet` swallows the error and returns `false`.
- Measured: after 52 weeks one slot holds 544,000 characters in `localStorage` (the save, about 270,000, plus its weekly backup). Browsers store these as two bytes a character, so about 1.1 MB a slot. Three slots are about 3.3 MB; a kept-aside unreadable save stores the save and its backup a second time.
- WebKit's limit for `localStorage` is about 5 MB an origin (check the exact figure in the wrapper). Past it, every save fails, the game keeps playing, and nothing says so.
- Suggested: show a banner when `saveGame` returns `false`; consider not keeping a backup for every slot.

### 2. Swapping storage for iOS is not the three-function change the header says
- `save.js`'s header says to swap `storageGet`/`storageSet`/`storageRemove` for Capacitor Preferences or Filesystem. Those are asynchronous; everything here is synchronous: `main.js` calls `loadGame()` and mounts at once, `setState` saves inline, and `getPref` is read while a screen draws (`hallArtOn`, the fight pace).
- Suggested: load everything into memory once at start (awaited before `mountApp`), read from memory, write behind. The rest of the game can then stay synchronous. Worth deciding before the wrapper work starts.

### 3. `confirm()` and `alert()` guard 13 actions
- `actions.js` uses `confirm()` for: selling gear (154), expanding a hall (193), opening a hall (201), removing a built piece (241), buying a hall (247), buying off a heist step (253), loading a file (409), a new game over a used slot (430), deleting a slot (439), restoring a kept game (444), discarding one (455), going back to the backup (459). `alert()` reports three errors (416, 450, 476).
- In a bare `WKWebView` these do nothing unless the app implements the dialog delegate, and `confirm` then returns `false`: the actions would silently stop working. Capacitor does implement them, as native system alerts, which will not look like the game.
- Suggested: one in-game confirm sheet in the skin's style.

### 4. Exporting a save will not work in a WebView
- `save.js exportSave` (236) and the kept-game download (206) build a `Blob` and click an `<a download>`. `WKWebView` does not download from that. The backup reminder (`BACKUP_REMINDER_DAYS`) points players at this button.
- Import uses a hidden file input, which iOS supports through the document picker; it should be checked on a device.
- Suggested: on iOS hand the file to the share sheet (a fourth function in `save.js`, beside the storage three).

### 6. Opening a job, and the Jobs tab, are slow on a long save
- With the CPU slowed 4x, on the 52-week save: opening a job took 888 ms (one sample); sending one 254 ms. On a new game: opening a job 121 ms median (13 samples), taking someone off the squad 261 ms.
- In Node at full speed, drawing the Jobs tab took 58 to 97 ms, against 1 to 3 ms for every other tab.
- Cause, by reading: each job card and the plan run the planning read (`jobs.js boardRead` → `squad.js jobRead`, which plays fight odds). `readCache` is keyed by the state object, and every change makes a new one, so the whole board is recomputed after any tap that changes the game.
- One tap in the new-game session took 3.7 s at 4x; I did not capture which action it was.
- Suggested: key the cache on what the read depends on (job id, crew, gear, heat) rather than the state object; profile on a device first.

### 7. Every tap redraws the whole page and writes the whole save
- `render()` replaces `root.innerHTML` (60,000 to 76,000 characters on Today). At 4x slowdown the median tap took 35 ms on a new game and 55 ms on the year save; 95% were under 100 and 123 ms. Usable, with little headroom on old phones.
- `setState` → `saveGame` stringifies the full state (about 1 ms at full speed) and then **parses the whole backup** (`readJson(backupKey)`) only to compare its day and seed. That second step is avoidable by remembering the backup's day and seed.
- Not urgent; listed so the iOS profiling starts from numbers.

### 8. The save is mostly inbox
- After 52 weeks: 269,000 characters, of which the inbox is 200,000 (93 messages, about 2,000 each: report timelines). Crew 48,000, the other tongs 16,000.
- This run (seed 1, fresh crew, hiring above ¥4,000) is over the 250,000 budget in `tests/inbox.test.js`; the test's own settings pass. `drafts/OWNER-ITEMS-battle.md` already notes seeds near the budget.
- It feeds finding 1: the inbox is the lever if storage gets tight.

### 9. The oldest iOS this will run on is 16
- CSS uses container units (`cqw`, `styles.css:1525`), which need iOS 16. `100dvh`/`100svh` (many places), `structuredClone` (every core function), `.at()` and `.findLast()` need 15.4.
- One plain `100vh` remains (`styles.css:1268`, the watch feed's height); on iOS it includes the area under the browser bars. In a full-screen wrapper it is harmless.
- Suggested: state "iOS 16+" as the target, or drop `cqw`.

## Low

### 10. Touch behaviour is not set globally
- Only the City map sets `touch-action: manipulation`. Nothing sets `-webkit-tap-highlight-color`, `user-select` on controls, `-webkit-text-size-adjust`, or `overscroll-behavior` on the page. In a WebView that means grey tap flashes, text selection and the copy callout on a long press, and rubber-band scrolling.

### 11. Two hints exist only as hover titles
- `citymap.js:100`: the 6 px yellow dot beside a district label means "Street talk" only in its `title`.
- `jobs.js:140`: the job card's risk corner says its level by colour, a `title` and an `aria-label`. If the level is not also written on the card, colour is the only cue on a phone.
- The six `:hover` rules in `styles.css` only change colours; none reveals information.

### 12. The UI edits the game state in place in three spots
- `actions.js:105`, `116` and `283` set `msg.read = true` on the live state and call `saveGame` directly, skipping `setState`. It works, but it is the one place the "core returns a new state" rule is bypassed, and these saves are also unchecked (finding 1).

### 13. The core reads the clock once
- `core/state.js:40`: a new game's default seed is `Date.now()`. Harmless in play, but it is why `npm run screenshots` never gives the same game twice, and it is the only clock read in `src/core`. Passing the seed from `main.js` would keep the core pure.

### 15. Size and shape
- `ui/actions.js` is 32 KB because `onClick` is one 28 KB `switch` of 142 cases. Splitting it by screen would be a restructure.
- `ui/styles.css` is 204 KB in one file: now the largest file a UI task opens. `ui/art.js` is 146 KB (a cut between faces and guns/gear exists) and `ui/districtArt.js` 59 KB.
- The build is one 1.67 MB script (500 KB gzipped), mostly job content. Loaded from disk in a wrapper this costs parse time only; not measured on a device.
- `app.js` has two doc comments stranded above the wrong function (above `topbarDate` and above `raidUnplanned`); they were like that before the split.

### 16. Things checked and found fine
- No DOM, `window`, `localStorage` or `Math.random` in `src/core` or `src/data` (the hits are words in content).
- `index.html` sets `viewport-fit=cover`; `styles.css` uses `env(safe-area-inset-*)` in seven places.
- No form field that would trigger iOS's zoom on focus (the only input is the hidden file picker).
- Timers: the fight stage's one interval is cleared (`fightstage.js:233`); the watch screen removes its window listeners when it stops.
- 19 looping CSS animations, with 20 reduced-motion blocks covering them. They keep running while the app is in view; worth a look only if battery use shows up.
- The service worker is registered only over http(s), so a `capacitor://` or `file://` wrapper will not try to.
- No page errors in any of the browser sessions (about 10,000 taps across steps 3 and 4).
