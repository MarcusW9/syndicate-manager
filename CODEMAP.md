# Code map

Where things live and how a run flows, so you can read a few functions instead of whole files. Rules (architecture, tests, docs, commits) are in `CLAUDE.md`; status and what's next in `HANDOFF.md`; why each choice was made in `DESIGN.md` (decision log rows in `docs/design/`). Keep this file short and current: when you move something, fix its line here.

See also `docs/ARCHITECTURE.md` (state shapes, economy loop, `finish()`, saves, tests).

## Layers (from CLAUDE.md)
- `src/core/` game logic, pure: state in, new state out. `src/ui/` the only DOM. `src/save/save.js` the only storage. `src/data/` content as data. `src/config/names.js` all placeholder names.
- Every roll is `d20 + stat >= 10 + difficulty` (`core/risk.js` `successChance`). Randomness: `nextRng(state)` (`core/random.js`, moves the state's counter) or `makeRng(seed)` (`core/rng.js`, doesn't). Never `Math.random()` in core.

## The run, in order
`startMission` builds `am` (the active mission, `state.activeMission`): a **queue** of steps, `beat | zone | incident | crisis | battle`, and `am.step` points at the next one. One function per step type, all returning a new state:

| Step | Function | File |
| --- | --- | --- |
| beat | `revealBeat` | `core/mission.js` |
| zone | `enterZone` | `core/mission.js` |
| incident | `runIncident` (roll, save, cost; an unsaved danger incident starts a fight) | `core/mission.js` |
| battle | `runBattle` (one round, then `afterRound`); a loud run's first guard always starts one (`loudFightDue`, `core/battle.js`) | `core/runbattle.js` |
| crisis | `describeCrisis` / `chooseOption` (the player's or the orders' choice) | `core/mission.js` |
| critical | `describeCritical` / `resolveCritical` (stabilise, extract, push on) | `core/mission.js` |
| call-in | `describePending` / `resolvePending` (`am.pending`: `alert`, `injury`, `door`, `standoff`) | `core/mission.js` |
| end | `finish` (pay, heat, reputation, growth, report), then `closeMission` | `core/mission.js` |

`core/autorun.js` `autoStep` takes the next step the crew can take on its own; `needsPlayer` says when to stop for a call-in; `autoRun` plays a whole hands-off job. `core/mission.js` sections are marked `// --- name ---`; `grep -n "^// ---"` finds them.

**Away jobs** (`core/away.js`, 2026-11-04): a crew sent away plays a share a day. `advanceAway` (the day tick, from `time.js`) steps each away job to today's stopping beat (`beatsByDay`, `dayDone` in `autorun.js`, which `needsPlayer` reads); one that needs the player waits (`waiting`) with a blocking `kind: 'callin'` message. `takeCall` puts it in `state.activeMission` (the watch screen); `letThemRun` hands it back at the day's end; `takeCommand` plays the rest now. Away crews fight on their own unless under command. `crewsOut` (with `phaseOf`, status and beat progress) feeds Today's crew-out cards; reports carry `back` for Today's back cards; quiet-day lines in `data/away.js`. Backlog for the command centre and presence: `drafts/ops-and-presence.md`.

## UI files
`ui/app.js` all screens and routing (one `state`, `setState` → save → `render`); `ui/board.js` the squad board and planning; `ui/watch.js` + `ui/siteplan.js` the live job (`ui/route.js` turns each site's route onto the grid with cut corners, for the plan and the mini maps; `ui/duel.js` the face-off over the map when a moment is one person's roll); `ui/fightorders.js` command fights; `ui/citymap.js` the Ops map (the command centre's neon map: districts, heat glows, crews' faces, call and raid rings; since 2026-11-07 the labels as HTML over it (`cityMapLabels`), the frame (`cityMap`) and zoom (`cityMapView`, eased by `animateMap` after `render()`, from `app.js mapView`)), Ops' Tonight list is `app.js citySummary`, `ui/districtArt.js` the district pictures, `ui/minimap.js` the crew-out cards' mini maps (the job's site, the route walked, the crew as still dots), `ui/hallbuild.js` the hall build screen (a hall's page › Build: the plan with its grid and beds, the palette, Place / Turn / Remove); a hall's own page is `app.js renderHallPage` (UI state `hallPage`, from Crew › Halls or Ops' district card, shown on that tab), `ui/landmarks.js` the district landmarks (beside the halls on Crew › Halls and the raid screens, `app.js hallMark`); `ui/gear.js`, `ui/art.js` (faces), `ui/icons.js`; `ui/styles.css` (the street-terminal skin is the second half).

## The watch screen
`ui/watch.js` runs the feed on a timer and hands each new card's `cue` to `ui/siteplan.js`. A fight waits for orders each round (`needsPlayer`): `ui/fightorders.js` draws the orders panel in the call-in slot and the map's overlay (`plan.command`), and app.js plays the round with `runBattle(state, orders)`, `handOffFight` or `pullBack`. Otherwise the watch hands each card's cue to `ui/siteplan.js`, which plays it on the site map; a fight's cue is `cue.battle` (`phase`, both sides' health, the round's `lines`), played by `fight()` in `siteplan.js`. Guards still ahead wait on their posts: `guardPosts(am)` (`core/battle.js`) → `plan.posts()`, at each site's `posts` spots. `core/feed.js` builds the cards and cues from `am.events`.

## Site maps
`data/sites.js`: plain sites, and districts drawn as parts (`PLOTS`: a plot with approaches, covers and targets; a target with `jobs` is that job's own place). `pickSite(district, jobId, templateId)` picks the parts from the job's id (stable, nothing stored) and `assemble()` makes them a site. The core reads a site only for fights: `core/fightspots.js` `fightSpots(site, zone)` puts both sides on spots behind the drawn cover (every district: `data/battle.js` `spotsIn`); `node scripts/preview-fightspots.mjs <district> <png>` draws them, `tests/fightspots.test.js` checks them. `ui/siteplan.js` draws it. `node scripts/preview-sites.mjs <district>` draws every combination; `tests/sites.test.js` checks each (geometry, routes clear of cover, a job's own target).

## Events and the record
Everything that happens in a run is `record(am, event)` into `am.events`. `feed.js` turns events into watch cards; `report.js` and the report's full log (`ui/app.js` `renderFullLog`) read the same events. A new kind of moment needs its event, a card in `feed.js` and a line in `renderFullLog`.

## Adding things
- **A call-in (pending kind):** `decisionChoices` and `ordersDecision` (`incidents.js`), `describePending` and `resolvePending` (`mission.js`), the title in `ui/app.js` (search `calling in`), a test that it has an exit.
- **A client:** data only, `data/clients.js` (+ `data/cast.js` for `{id}` tokens); the checklist is `docs/ARCHITECTURE.md` "Adding a client", `tests/clients.test.js` checks it.
- **A job:** a file in `data/missions/`, imported in `data/missions.js` and listed in `MISSIONS`, its id in a client's `jobs` (`data/clients.js`); a hall's opening favour instead in `data/halls.js` (`HALL_SITES[d].opening`, asked by `.contact`; `isOpeningJob`). Check it first with `node scripts/check-job.mjs <file>` (`core/jobcheck.js`; `--all` checks every job). Drafting prompt: `docs/new-job-prompt.md`; adding a drafted job: `/add-job` (`.claude/commands/add-job.md`).
- **An incident:** `data/incidents.js` (and `ZONE_POOLS`), district lines in `data/districtIncidents.js`; `tests/incidents.test.js` checks the shape.
- **Gear:** `data/gear.js`; the rules read it in `core/gear.js` (and `core/battle.js` for fights). Looks and names: `core/looks.js`, `data/gearLooks.js`. A sidearm's strengths: its frame and rolled quirk, `core/gear.js` `sidearmStats` (`SIDEARM_FRAMES`, `SIDEARM_QUIRKS`); perks would sit beside the quirk.
- **Changing the state's shape:** bump `SAVE_VERSION` in `core/state.js` and add a migration in `save/save.js`.
- **A roll modifier:** it must show in the roll's notes and in the planning read (`coverage`), or the shown risk lies.
